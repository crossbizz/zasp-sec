# Managed Windows inventory pilot

The Windows agent registers an assigned device, sends signed health and uploads an employee's local skill and MCP installation metadata. It supports one assigned Windows SID and one personal, managed or project collection scope per enrollment. The base assignment reports inventory-only coverage and leaves the policy acknowledgment empty. A second optional assignment installs the Claude Code pre-tool broker for the enrolled employee. Inventory alone cannot establish execution, enablement or target effect.

## IT deployment

1. Build `go -C services/endpoint-agent build -trimpath -o zasp-device-windows.exe ./cmd/zasp-device-windows` for Windows amd64 or arm64. Authenticode-sign it with the organization's approved release identity, publish the SHA-256 digest of the signed bytes and the signer thumbprint. On Windows run `Stage-Device.ps1 -SignedExecutable <file> -AgentSHA256 <digest> -SignerThumbprint <thumbprint> -NewOutput <new-directory>`. It validates both pins. Use Microsoft's IntuneWinAppUtil to package the staged `input` directory with `Manage-Device.ps1` as the setup file. Use the generated standalone detection script. Sign the deployment scripts with the organization’s approved signer when the managed Windows execution policy requires signed PowerShell.
2. Deploy the [employee-context CLI](../intune-cli/README.md). Assign the new device Win32 app using **System** install behavior and **64-bit Windows PowerShell**. Set `Manage-Device.ps1 -Action Install -AgentSHA256 <digest> -SignerThumbprint <thumbprint> -EmployeeSID <SID> -Scope personal`. Select `managed` for managed inventory or `project` to scan a single assigned project directory. At sign-in, the employee task arms filesystem notifications and takes an initial inventory. Adding, editing, renaming or deleting a file in an assigned skill root triggers a scan. It combines bursts of changes, including directory copies, and reconciles its assigned roots after a notification overflow. The separate LocalSystem task wakes on writes to the protected report and retries pending delivery on its five-minute heartbeat. Rapid changes can be combined in the latest on-device snapshot. The LocalSystem transport reads a fixed file whose DACL grants that user write-data. It rejects alternate file links or reparse points and never opens paths contained in the report.
3. The installer prints a per-device Ed25519 public key. Retrieve it over the existing authenticated MDM management channel. Re-running `zasp-device-windows.exe init-device-key` in LocalSystem context returns the same public key. Create a dedicated Environment `sync_endpoint` credential and pre-register the public key, transport token ID, cohort and independently held issuer public key using the Devices enrollment screen. Use separate credentials for every device.
4. Provision the resulting nonsecret `device.json` under `%ProgramFiles%\Zasp Inventory Device`, with owner SYSTEM or Administrators and inherited read-only employee access. The binding and SID must exactly match registration and deployment. Example:

   ```json
   {"origin":"https://zasp.example.com","binding":{"organization_id":"ORG","workspace_id":"WORKSPACE","environment_id":"ENVIRONMENT","device_id":"DEVICE","credential_generation":1},"scope":"personal","assigned_sid":"S-1-5-21-111-222-333-1001"}
   ```

   For a project assignment, set `scope` to `project` and add `"project_root":"C:\\Repos\\Support Agent"`. The employee task checks the selected project's `.claude/skills` and `.agents/skills` at sign-in and when their contents change. It also watches the project MCP declaration. The device keeps the configured project path local. Reassignment uses the same retirement and enrollment process as changing the assigned user.

5. Through a separately authenticated per-device secret-delivery service running as LocalSystem, pipe the unique transport PAT from the provider directly to `zasp-device-windows.exe provision-token` on standard input. Keep secrets out of package files, Intune command arguments and task transcripts. User-profile DPAPI seals the transport secret, signing seed and local queue under LocalSystem with distinct purposes. This is a software-backed key. The generic installer carries no fleet-wide enrollment authority.
6. After the employee signs in and the CLI and device assignment are present, the employee task starts scanning automatically. The transport starts at installation and boot. `zasp-device-windows.exe status` as LocalSystem returns the device ID, last confirmed heartbeat and pending snapshot count. The assigned employee can run `zaspctl device status` or `zaspctl device doctor` to read a limited LocalSystem-published health summary from the 64-bit HKLM registry. It identifies the optional broker separately and considers telemetry stale after 15 minutes. Inspect central Devices → device → Local inventory. Windows sends device-keyed installation and partition references, available manifest digests and completeness. For scanned skills it also sends the ruleset and aggregate finding and skip counts. Source files and project paths stay on the device. The queue preserves a prior complete snapshot across a later partial scan and retries rejected uploads. A quiet or unsigned-in laptop retains its historical evidence. Task scheduling and central observation are separate statuses.
7. Remove the optional pre-tool assignment first, then retire the device server-side before removing the enrollment app. The next exchange will be denied. Use the same release pins with `Manage-Device.ps1 -Action Uninstall` to remove both scheduled tasks, the executable, the employee collector, its plaintext handoff and its health summary. The sealed queue and protected credentials remain for the organization's controlled recovery. Archive required evidence, then remove retained data using IT's offboarding process. Provision a new key, credential, clean state and assignment when changing employee or rotating the device identity.

## Validation

The portable integration test sends real device signatures over TLS and checks retry, retained partial inventory, de-duplication, absence of policy acknowledgment, and rejection after retirement. The native Windows CI tests exercise profile-bound DPAPI tamper and purpose checks, access-control descriptor validation, PowerShell parsing and rejection of unsigned packages. A live release requires an approved Authenticode signer, real Intune assignment, the operator's per-device secret-delivery channel and a signed-in employee. Confirm install, upgrade, user-context scan, offline recovery and uninstall on the targeted Windows configurations before promoting the pilot.

## Optional managed Claude Code hook

Deploy this Win32 assignment after the inventory app, device binding and unique credential are provisioned. Use the same staged payload and release pins. The broker serves one assigned employee on one managed workstation. This workflow requires the Windows native Claude Code runtime to invoke its synchronous PreToolUse hook. Other applications and shells do not acquire coverage from installing the broker.

1. In Devices, use the same independent Ed25519 issuer public key as enrollment. Sign the scoped V2 envelope and assign it to the device. Start with monitor mode. Provide canonical absolute employee-home and workspace paths on a local fixed drive. Use a dedicated user workstation because Claude’s machine-level settings apply across user profiles. An unassigned user contacting this hook gets its unavailable action.
2. Set the second Intune Win32 assignment to depend on the enrolled device app. Use the generated `Detect-Pretool.ps1`. For **System**, 64-bit Windows PowerShell, the install command is `Manage-Pretool.ps1 -Action Install -AgentSHA256 <signed-release-hash> -SignerThumbprint <thumbprint> -IssuerPublicKey <base64-public-key> -EmployeeHome C:\Users\employee -Workspace C:\Work\project -OnUnavailable continue`. Choose `deny` for deployments that should block the matching callback even if the broker or policy is unavailable. The signer key here is public. Each device keeps its signing key and transport token sealed under its LocalSystem DPAPI profile.
3. With an empty Claude settings location the installer writes a machine-managed hook covering the supported Claude tool families in `%ProgramFiles%\ClaudeCode\managed-settings.json`, starts a LocalSystem startup task and records the precise file digest. If another product already owns the file, have IT merge the hook below and supply `-ExistingManagedHook`. The installer verifies that exact synchronous hook and leaves externally managed settings under IT ownership. Restart Claude Code to load changed settings.

   ```json
   {"hooks":{"PreToolUse":[{"matcher":"^(Bash|Read|Write|Edit|MultiEdit|Glob|Grep|WebFetch|mcp__.*)$","hooks":[{"type":"command","command":"\"C:/Program Files/Zasp Inventory Device/zasp-device-windows.exe\" claude-pretool-open","timeout":3}]}]}}
   ```

   Set the last word to `claude-pretool` for transport fallback `deny`. A responding broker with an authenticated policy applies its signed mode and failure mode. An expired enforce/closed receipt has reason `policy_expired`. A monitor-mode expiry continues the call. An unavailable response from an untrusted server or missing signed policy invokes the independently configured hook fallback.
4. Run the sync scheduled task. `zaspctl device doctor` shows the last broker probe, policy state/revision/mode, pending signed receipts and observed drops. Fleet receives `windows_claude_pretool_v2` plus `verified_cache` only when the pinned SYSTEM pipe responds for the same configuration and a signed unexpired cache is present. This establishes broker health. For rollout, also exercise a harmless allow and deny in the actual managed Claude client and check signed observations. Receipts contain opaque action and session references, reason and rule. Skill identity, execution and target effect stay unknown.
5. Uninstall this second assignment with `Manage-Pretool.ps1 -Action Uninstall -AgentSHA256 <digest> -SignerThumbprint <thumbprint>`. It stops the broker and removes its configuration and unchanged owned hook. For externally managed settings, remove the hook through the original settings owner. A locally edited owned file needs reconciliation before automatic removal. The sealed evidence queue remains for controlled recovery.

For a task-bound ticket adapter, supply the public verifier JSON to `Manage-Pretool.ps1 -DelegationVerifier`. The verifier contains the three enrolled tenant IDs, `parent_task_id`, `agent_id` and a base64 Ed25519 `public_key`. The installer selects the synchronous `claude-pretool-delegated` command with a catch-all matcher and deny fallback. With externally managed settings, install that exact command and matcher. Pass the child grant privately in `ZASP_TASK_DELEGATION` for the task process. The broker verifies the actual ticket destination before normal policy and denies missing, expired, unsupported or out-of-scope calls.

The native Windows workflow exercises the same pipe with a disposable LocalSystem server and a separate assigned user, using synthetic actions. It checks the ACL for an unassigned SID and verifies persisted receipt signatures. Customer Authenticode signing, actual Intune targeting and hook invocation in the deployed Claude Code build require a managed pilot.
