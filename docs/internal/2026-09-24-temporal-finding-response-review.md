### Important 1 — Unify note acceptance before persisting a plan or effect

`services/platform/migrations/sql/0078_production_temporal_finding_response.planning.sql:72` uses one-argument `btrim(note)`, which trims ordinary spaces only. The new public Go validator at `services/platform/apiserver/security_agent_action_details.go:99` uses `strings.TrimSpace`, and `apps/web/api/decoders.ts:596` uses JavaScript `trim()`.

For example, a provider candidate whose note is `"\u00a0Investigate exposure"` passes the SQL byte, trim and control-character tests: NBSP is not an ordinary space or a control character. It fails both public validators. SQL invokes this candidate predicate for parsing/admission, and `services/platform/migrations/sql/0078_production_temporal_finding_response.effect.sql:85` can consequently authorize and commit an autonomous effect that the run-detail API cannot decode. A supervised proposal becomes unreadable before an approver can act. The immutable metadata makes this more than cosmetic input normalization.

There is also a Go/JavaScript boundary difference for leading U+FEFF: JavaScript trims it while Go does not. Define one explicit whitespace/control policy across SQL, Go, the UI decoder and OpenAPI; reject disallowed notes before durable plan admission rather than silently changing the approved text. Add focused installed/parser-to-readback regressions for NBSP, U+3000 and U+FEFF, covering both supported statuses and supervised/autonomous paths. The existing SQL status-loop fixture uses only an ASCII note and does not cover this mismatch.

This finding is established by the candidate predicates and the inherited parser, not by rerunning the installed suite. The inherited parser's Unicode boundary-space check applies to `summary`, not to the new step `note`.
