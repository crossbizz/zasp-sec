## Framework support and verification

Select **Compliance → Framework coverage** for a release-pinned index. Each row carries its source edition, review owner, applicable surfaces, evidence kinds and recorded verification date. A newly cataloged technique starts without prevention evidence. Use the edition and Environment selectors when exporting a result for a customer.

| Adapter or source | Operation and data mode | Evidence available to a reviewer |
| --- | --- | --- |
| zaspctl static v2 | Scan local employee, project and managed skill directories offline. Share findings-only or submit an authorized private archive. | Add-on version, manifest digest, ruleset, file findings and coverage gaps. A finding identifies a static signal. |
| Python SQLite context v1 | Approve and version memory, document and artifact manifests. Retrieve with tenant and reader checks. Compare a proposed field to its authoritative value or test a synthetic output marker. | Scoped runtime decision, typed outcome and locally committed target receipt. Losing the target recorder leaves the outcome unknown. |
| Python SQLite workflow v1 | Bind purpose, approval, handoff audience, retries, fan-out and action count to a scoped run and receiving queue. | Reported action outcome plus independently inspectable queue state. The action meter counts accepted operations on this adapter. |
| Endpoint signed ticket pair | Exercise the same target with allowed and protected actions under one bound policy revision. | A verified-prevention claim requires the authorized pair with independently trusted adapter and target attestations. |
| Cloud posture and keyed add-on evidence | Review a mapped inventory condition or attributable static finding in the current Environment. | The coverage view retains separate counts for posture, static analysis, runtime observation, tested controls and verified prevention. |

The pilot counts a verified prevention for 30 days from the end of the independently corroborated test window, inclusive. Reimporting a run does not renew its date. The coverage table retains the last verified date and historical evidence after expiry. Rerun the control and protected pair on the same scoped policy and adapter to renew current coverage. Archived exports retain both the status and collection time used when the report was requested.

An Environment-wide coverage read or edition export accepts up to 2,000 candidate evidence rows and 8 MiB of candidate metadata before rule matching. A skill version can contribute several candidates, one per rule. The API returns an error beyond either limit so a partial result cannot stand in for the full denominator. To inspect an individual item in a larger Environment, open its add-on or session detail and select **View framework references**, or call `GET /api/v1/compliance/coverage/evidence` with its `source_kind` and `source_id`. This lookup applies the same source permissions and bounds directly to that item. Edition and evidence-kind filters do not lower the Environment-wide input budget.

The candidate's CI run identifies the tested commit and platforms. Record provider, OS and harness versions and verification dates separately for each live rollout. [Pilot evidence and verification](pilot-verification-evidence.md)

## Release and deployment evidence

- **Browser consent and findings sharing.** On sealed release 5 with PostgreSQL 18, Linux Chromium 156 loaded the signed-in Environment, cleared the login URL fragment and enabled approval after entry of the terminal code. The API accepted the scope and CSRF checks. The PKCE exchange issued a findings-only credential after approval and returned HTTP 409 for both a pending exchange and a replay. Using that credential, `zaspctl` scanned a harmless local skill and submitted it twice. Both submissions returned the same receipt. The signed-in browser read the matching manifest digest with a pending review. The local fixture seeded the session and supplied the OpenFGA decision and projection. To verify the remaining pilot steps, sign in through your identity provider, run `zaspctl auth login --environment ENVIRONMENT_ID` using your operating system’s credential store and open the receipt in **Tools & MCP**. [Local scan and sharing walkthrough](../getting-started/local-skill-scan.md)
- **Developer download.** The default console offers a source build. The release owner can prepare tested native CLI candidates, sign the manifest offline, stage it against the trusted release key, and enable versioned downloads in **Scan this device**. Complete applicable Apple or Windows signing and enrollment checks before declaring a platform ready for distribution. [CLI release and reversal](../../deploy/cli-release/README.md)
- **Native runner evidence.** The Linux, macOS and Windows jobs passed on commit `f29556b3`. That result covers the code paths listed in the workflow. For a later candidate, use that candidate’s own check results. [Native CI run](https://github.com/crossbizz/zasp-sec/actions/runs/44984770358)
- **Database and API.** Run `scripts/test-feature-v2-upgrade.sh` from a checkout with its predecessor in Git history, Go, Node and PostgreSQL 18 available. The script creates its own temporary cluster, upgrades a populated database, compares its catalog to a fresh install and exercises the installed product paths. Environment access, credentials and graphs for deployed customers are separate from this test.
- **Pilot rollout.** Enroll the selected devices, start in monitor, issue one signed canary revision and check its acknowledgment. Record allowed and protected action IDs with independent recorder evidence. Retain offline devices in the rollout denominator. A rollback publishes a higher revision and remains pending on disconnected devices until acknowledgment.
