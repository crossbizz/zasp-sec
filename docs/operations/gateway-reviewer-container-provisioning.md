# Reviewer publisher container provisioning

The publisher image selects UID and GID 65532. Provision a dedicated destination directory owned by that UID with mode 0700 before starting it. The verifier must use the same UID to read the published credential. Mount only this private destination writable; keep the root filesystem and projected-token source read-only. Drop all capabilities and prevent privilege escalation.

The source must retain the publisher's supported projected-volume layout: a `token` symlink to `..data/token`, with `..data` selecting one confined generation. A locally verified configuration uses root-owned generation directories with mode 0755 and root-owned token files with group 65532 and mode 0440. This configuration establishes local filesystem compatibility. Actual Kubernetes projected-volume ownership and mount options must be checked separately; do not broaden directory permissions or token access to force admission.

On 2026-10-17, the locally built scratch image ran successfully with its default UID, a read-only root filesystem, read-only source mount, all capabilities dropped, no privilege escalation and no network. Dedicated Docker volumes were provisioned explicitly. The check observed initial publication, generation rotation, UID/GID 65532 ownership, mode 0600, one link, and joined SIGTERM withdrawal. All owned containers, helper containers and volumes were removed. The first provisioning attempt failed because it tried to change directory mode after changing its owner without the required capability. Set the private directory's mode before transferring ownership. The original failure and independent review findings are preserved in the evidence archive.

This check used synthetic local tokens. It establishes neither real Kubernetes token authentication nor reviewer RBAC, fsGroup provisioning, sidecar activation, verifier integration or deployed rotation. The image exists locally; this check does not publish a registry digest, provide image attestation or clear release guards.
