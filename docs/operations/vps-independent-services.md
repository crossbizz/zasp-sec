# Independent services with the VPS CLI

The VPS component commands operate on OpenBao and Nango independently. A managed component installs its bundled Helm chart at version 0.1.0 from this Zasp checkout. Both Helm charts require immutable runtime image digests. An existing component stays under its current operator. The CLI can check its health and credentials. The Zasp application has a separate release boundary.

Run commands against a private configuration generated by `./zasp --profile vps config init`. For cluster operations, set explicit `ZASP_VPS_KUBE_CONTEXT`, `ZASP_VPS_CLUSTER_UID` and `ZASP_VPS_INSTALLATION_ID`. Compare the kube context and cluster identity to an independent infrastructure inventory before recording them. The UID belongs to the `kube-system` namespace. Use a lowercase DNS label for the installation ID. Component namespaces must be dedicated to that installation.

```sh
kubectl --context "$ZASP_VPS_KUBE_CONTEXT" get namespace kube-system -o jsonpath='{.metadata.uid}'
```

## Prepare and install

| Configuration | OpenBao | Nango |
| --- | --- | --- |
| Ownership | `ZASP_VPS_OPENBAO_MODE=managed` or `existing` | `ZASP_VPS_NANGO_MODE=managed` or `existing` |
| Dedicated namespace | `ZASP_VPS_OPENBAO_NAMESPACE=openbao-system` | `ZASP_VPS_NANGO_NAMESPACE=connectors` |
| Managed chart values | `ZASP_VPS_OPENBAO_VALUES_FILE` | `ZASP_VPS_NANGO_VALUES_FILE` |
| Operator TLS trust | `ZASP_VPS_OPENBAO_CA_FILE` or trusted system roots | `ZASP_VPS_NANGO_CA_FILE` or trusted system roots |
| Operator readiness credential | `ZASP_VPS_OPENBAO_STATUS_TOKEN_FILE` containing a scoped token with read on `auth/token/lookup-self` | `ZASP_VPS_NANGO_SERVICE_KEY_FILE` containing the Nango environment service key |
| Optional explicit HTTPS authority | `ZASP_VPS_OPENBAO_URL=https://openbao.openbao-system.svc:8200` | `ZASP_VPS_NANGO_URL=https://nango.connectors.svc.cluster.local:8443` |

The URL must match the configured namespace and the production chart authority. For an existing service configure that same DNS name, certificate SAN, private routing and policy. The operator machine must resolve and reach its existing private endpoint. An arbitrary public Nango origin is rejected. Managed status uses a short-lived loopback-only Kubernetes port forward to the selected service or OpenBao pod and verifies the original service DNS name over TLS.

Use absolute paths. Keep private credentials in a root- or operator-owned mode-0600 file in a protected directory. CA bundles, public PGP keys and Helm values can be readable but may only be writable by their owner. The operator needs Python 3 with PyYAML, Helm 3 and kubectl. Install GnuPG on the operator workstation for OpenBao initialization.

1. Pin the Kubernetes context and cluster identity. Prepare OpenBao chart values with an immutable image and a persistent storage class, and Nango chart values with an immutable TLS proxy image, the stable public Zasp origin matching the installation’s `ZASP_ORIGIN`, permitted clients, database address ranges and provider egress ranges. Create durable, independent PostgreSQL storage for Nango and provision its encrypted offsite database backups. The Nango chart owns its service and migration job. Keep the same Nango encryption key for the life of its encrypted credentials. [OpenBao values and certificates](openbao-vps.md) · [Nango values, credentials and database](independent-nango.md)
2. A first `install COMPONENT` validates the chart and creates the dedicated namespace with label `zasp.io/installation=<installation-id>` if it is absent. It then reports required TLS, CA or credential objects that still need to be provisioned. Supply the objects described in the service runbooks. A pre-created namespace must already have that matching label. Review the actual owner before labeling a pre-existing namespace. A namespace owned by another installation fails closed.
3. Re-run `install` after supplying the inputs. The CLI checks Secret key names and the existence of required ConfigMaps. It keeps their values out of operator output. A previously deployed Helm release is left in place. Orphaned resources, an existing Raft volume with no release, or a failed/pending release require a recovery review, to protect persistent state and previously run Nango migrations.
4. Finish OpenBao initialization and unseal before delivering scoped credentials to workloads. Verify the stable HTTPS OAuth callback and tenant mapping before connecting existing Nango credentials. If Nango has no integrations its status explicitly reports the missing provider setup.

```sh
./zasp --profile vps install openbao
./zasp --profile vps status openbao
./zasp --profile vps install nango
./zasp --profile vps status nango
```

## Secure OpenBao operator handoff

Initialize on a trusted, **off-VPS** workstation with the pinned kube context, protected kubeconfig and verified CA. The workstation must reach the cluster's private control plane. This command uses a local private tunnel and never copies custody material into Kubernetes. For a managed installation, supply these additional settings only on that workstation:

- `ZASP_VPS_OPENBAO_PGP_KEYS_DIR` is an absolute protected directory containing binary **public** OpenPGP encryption keys called `custodian-1.gpg` through `custodian-5.gpg` and `root.gpg`. Independently verify all six fingerprints against their custodians. Use distinct currently valid recipients. Each custodian retains its own decryption key. Keep a separate bootstrap operator for the initial root token.
- `ZASP_VPS_OPENBAO_HANDOFF_FILE` is an absolute new filename in a private mode-0700 directory on independent protected storage. The command reserves the file exclusively and synchronizes it before requesting initialization. OpenBao encrypts the five shares and bootstrap token to the specified public keys before returning them. The output file is mode 0600 and contains only the encrypted packets and installation identifiers. Normal command output never contains the packets or clear values.

```sh
./zasp --profile vps secrets init openbao
./zasp --profile vps status openbao
```

The threshold is three distinct shares out of five. Securely deliver each numbered packet only to its corresponding custodian, and the bootstrap packet only to its recipient. A packet is base64 encoded OpenPGP data. For example, on custodian 1's private workstation, decrypt their supplied packet privately with `base64 -d < custodian-1.packet | gpg --decrypt`. Do not run this in a logged or recorded terminal. Run the following command independently for each of three custodians, each using a protected connection to the correct host. The prompt disables echo. It rejects piped input and command-line shares.

```sh
./zasp --profile vps secrets unseal openbao
```

The command queries seal state before submitting one share. Repeating it on an unsealed service is safe. A restarted Shamir instance needs the threshold again. Use the bootstrap token only for initial operator access and scoped policies, including a separate status identity, and revoke it after independently testing those policies. Use the workload credential rotation procedure for API/discovery/signing/verification identities. Auto-unseal uses an independent external seal service and a separately rehearsed recovery design. [Policies, unseal and snapshot restore](openbao-vps.md) · [Workload token rotation](openbao-workload-projection.md)

Interrupted initialization is a special case. Check service state and the independently retained handoff. A complete handoff can be reused if the server initialized. A `pending` file records a request whose outcome may be unknown. If the server remains uninitialized, preserve the pending file, select a new handoff filename and retry. If it initialized but there is no complete recoverable response, the threshold shares cannot be generated again. Keep the node fenced and engage the recovery operator. Any decision to rebootstrap a confirmed empty installation is separate from this CLI. It will not reset a volume or reprint earlier shares.

## Operations and upgrade boundary

| Command | Managed service | Existing service |
| --- | --- | --- |
| `install COMPONENT` | Validates the local pinned chart and checks release/namespace ownership. A new OpenBao release can be installed while sealed. Nango waits for migrations and readiness. | Verifies live authenticated health. |
| `start COMPONENT` / `stop COMPONENT` | Scales only its explicitly selected Helm-owned workload. The mutation includes current-replica and resource-version preconditions. Stopping retains data. Starting OpenBao reports the custodian action needed if it is sealed. | Start probes the service. Stop must be performed by its owner. |
| `status COMPONENT` | Reports uninitialized, sealed, unauthenticated, unavailable or healthy. Missing optional Nango provider setup is shown separately. | Uses verified direct HTTPS with the scoped credential. |
| `logs COMPONENT` | Reports counts of Normal/Warning/other Kubernetes workload events. Event text, raw provider request logs, secret values and pod environment are excluded. | Use the service owner's protected operational logs. |
| `upgrade COMPONENT` | Stops before invoking Helm. The generic archive receipt proves ciphertext integrity but does not establish a completed restore for this installation, component and current release. | The external service owner controls upgrades. |

For a manual upgrade, record cluster UID, installation ID, namespace, Helm release name/revision/chart version and current image digests. Quiesce writes, capture the service-native snapshot and independent keys, and prove a restore into an isolated replacement. Verify OpenBao seal material, a KV canary and old Transit signatures, or a Nango database read and authorized connection under the preserved encryption key. Bind the evidence to those exact installation/release identifiers in the operator change record. Review the target chart, pinned images and migrations. Then upgrade only that service in its dedicated namespace and check readiness and client operations before resuming. If acceptance fails, fence the new writer and restore the appropriate database or snapshot onto a fresh volume before redirecting clients. Reapplying an older chart cannot reverse a database migration. [Offsite archives](offsite-backups.md)

The CLI unit tests include a real verified TLS socket, a wrong-host failure, redacted output, ownership/replica checks and create-only encrypted handoff behavior. On a host with Docker and GnuPG, the disposable drill runs the operator code against a fresh non-development OpenBao Raft server, with six generated OpenPGP recipients and three separate share submissions. All test decryption keys exist only in a disposable directory.

```sh
python3 deploy/zasp/vps_services_test.py -v
ZASP_TEST_VPS_OPENBAO_CLI=1 python3 deploy/vps/openbao/tests/restore_drill.py
```

These checks do not install a customer cluster, perform a real Nango callback or qualify a full application release on a VPS.
