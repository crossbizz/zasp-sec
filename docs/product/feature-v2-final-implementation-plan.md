# Zasp Feature V2 — final implementation plan

**Decision.** Ship private laptop skill discovery as the first usable release. Follow it with a review link that a developer can send to AppSec, then prove one governed tool action on a managed Mac. Use the original plan for evidence integrity and rollout order. Use the Neon plan for the developer handoff, explicit failure tests, and release measurements. A team can stop after any published milestone and keep using what it has adopted. Existing customers can continue to start with a read-only cloud or GitHub connection.

**Planning baseline.** This is the proposed build sequence for Zasp at commit `2f2ad720`. The comparison uses the two supplied files, `feature-v2-implementation-plan.md` (“original”) and `feature-v2-implementation-plan-neon.md` (“Neon”). Commands, APIs, thresholds and screens described as deliverables below are proposals. The build team should record the exact versions it verifies before publishing support claims. Both plans cover all seven feature headings. The practical difference is **when a customer can complete a job**, and **what evidence supports the result**. A laptop scan requires neither Jamf nor a cloud account. A fleet enforcement claim needs a managed device, a working pre-action adapter and an independent target receipt. These are different release decisions.

## What users will do

1. **A developer checks a local install.** From Overview → **Scan this device**, download the signed CLI for a supported OS, or go directly to the CLI instructions. Run the two local commands below with networking disabled. See managed, personal and selected project copies, including uncommitted edits, and the roots skipped. Open a self-contained local report. A clean run says **No findings from this scan** and names its rule set and coverage. Installation alone shows **Usage unknown**. This also works for a developer whose employer has never installed Zasp.
2. **The developer hands a finding to AppSec.** Select **Share findings**, preview the fields leaving the device, sign in in the browser, pick an Environment, and submit. The CLI returns a receipt and a deep link to the version in **Tools & MCP → Add-ons**. The detail has **Versions**, **Installations**, **Scans** and **Usage** tabs. It shows what the add-on could reach alongside what this scan actually found. AppSec compares a trusted CI observation for the GitHub commit with the local copy, sees which file classifications or dependencies changed, and approves, rejects or revokes an exact version and allowed origins. If a private file was skipped, the review shows **Partial** and explains how to rescan. After revocation, show which adapters acknowledged the change, which can prevent a load, and which installations still need removal and a confirming rescan. A teammate without access gets the existing scoped access response.
3. **An IT admin covers a pilot group.** In **Sources → Sensors → Devices → Enroll pilot**, select Environment, managed group, platform, data categories and collection cadence. Deploy the signed package and profile. The dashboard shows, for example, “3 assigned · 2 checked in · 1 offline · 2 acknowledged revision 7.” Selecting the missing device gives last contact and a repair step. The employee can run `zaspctl device doctor` without access to the fleet. **Connect a source** remains available to customers starting with GitHub or cloud discovery.
4. **An AppSec engineer tests a rule with an agent owner.** In **Guardrails**, select a named staging ticket action and a cohort, inspect monitoring results, and enable enforcement for that action. A developer sees the blocked operation, a decision reference, the reason, and a next step such as requesting the approved destination. In **Sessions**, the owner sees who issued the decision, which revision was applied, and what the target observed. The same view can show an edited skill installed on the laptop with no evidence that it ran.
5. **A responder verifies and releases a control.** From the session, preview affected adapters, scope and TTL, request containment, obtain the existing approval and check readback. An offline target stays pending. An unrelated session continues. The responder releases early or sees expiry and verified recovery. The security lead opens a pilot report with real evidence, omissions, and a link to the tested release and cohort.

Proposed first-use CLI, with the report written to a user-selected local path:

```bash
zaspctl addons inventory --local --project . --report-html ./zasp-inventory.html
zaspctl addons scan .claude/skills/ticket-helper --local --json > scan.json
zaspctl auth login
zaspctl addons submit scan.json --mode findings-only --environment ENV_ID
```

The first two commands require no sign-in, telemetry or network access. Local HTML escapes untrusted names and scan evidence and loads no remote assets. The submitted report uses an allowlist of safe fields, even if the local report contains paths. CLI stdout in JSON mode carries one versioned result with completeness and skipped reasons. Diagnostics go to stderr. Exit codes are `0` completed, `2` input/auth error, `3` incomplete/unavailable and `10` a complete scan violating an explicitly selected CI threshold. An interactive finding is a successful scan. Keep `./zasp` as the deployment operator's command.

**Manifest and installation.** Version the canonical encoding. Digest a sorted list of normalized relative paths, byte lengths and hashes under the declared root, preserving bytes and case. Use root-confined reads, skip links/junctions, reject collisions and changes during enumeration, track declared exclusions and bound time, size and file count. Keep local paths local. A skipped required file yields a partial observation with no approvable digest. Track executable attributes where reliably observed as separate execution evidence, and require equivalence for any approved policy that depends on those attributes. Track origin, signer/commit provenance, resolved dependency and remote schema separately from content identity. Model personal, managed, project, enabled plugin, configured extra and synced roots as distinct sources. A SaaS-only add-on can have provider provenance with local bytes unavailable. Remote MCP declarations supply metadata. Discovery never starts the named server. Reconcile complete per-device/per-root generations in order. Authenticate snapshots by device, user/profile and root partition. A complete newer partition can mark previously observed installations removed. A partial or late one cannot.

**Decision and outcome.** Scope uniqueness to (Environment, authenticated binding, action ID). The request contains a stable action ID, adapter session and tool-call ID where present, operation, classified target and verified references. Store the canonical input digest and immutable decision receipt atomically. Apply the existing idempotency-key conventions to retried mutations and expected-revision checks to reviews and policy changes. Preserve the wire status codes already used by existing routes. Identical authorized retries get the same receipt. A conflicting target or operation under the same key returns `409 action_id_conflict`. The receipt exposes revision, source, mode, verdict, would-block reason, coverage and next step. Outcomes independently describe dispatch, adapter application, target effect or unknown. A transport failure has its own reason. Late outcomes can add evidence without changing a decision. Queue local receipts with their actual time and revision. Handle bounded spool overflow with a dropped-count/gap record. A decision API retry must never redispatch the underlying tool.

**Evidence and permissions.** Store source, scope, trust level, observed/received times and stable IDs for each fact. Authenticate before returning any prior result. Use exact joins for attested shared IDs, retain inferred associations with justification, and show unknown on overlap or mismatch. Browser/provider events deduplicate only on trustworthy shared identifiers. Otherwise show both observations with their source. Map OpenTelemetry GenAI attributes to actor/session/tool-call references where the source supports them. A trace supplied by an unbound client remains a claim. Persist record and outbox event in one transaction. Idempotent workers update projections using aggregate revisions. Test browser, device, developer CLI, CI, provider and worker roles across two Environments, including guessed IDs, replay, stale revisions and revoked authority. Default to metadata-only collection. Private source storage, optional model-assisted analysis and optional behavioral jobs each have distinct consent, access, deletion and egress controls.

## Proof, promotion and rollback

**First enforcement experiment.** Use a customer-authorized non-production ticket fixture with synthetic records. Pin the adapter, policy, cohort, target and test window. Send an allowed control through the governed path and verify a durable target receipt. Exercise the protected operation with a distinct action ID and verify the applied denial and target state. Require an independent healthy recorder with a completeness watermark or a readback covering the observation window. A correlated unexpected write produces `unexpected_effect`. With full evidence, the expected result produces `passed`. Missing coverage, a failed control, or unavailable readback produces `inconclusive`. An unsupported capability produces `unsupported`. Preserve existing response-marker test results under their own test kind. Use this manual test for E and automate it in H. [Existing test probes](../../services/platform/redteam/probes/catalog.go)

These are **proposed pilot targets**, to be calibrated on the agreed hardware, corpus and real provider limits. Record numerator, denominator, elapsed time, sample size and test conditions with the result.
