# Zasp Feature V2

**Status** Proposed product requirements. The UX, commands, and new API operations below describe intended behavior. The existing product and its release gates remain the baseline for the implementation plan.

Zasp V2 connects the code and add-ons an agent is configured to use, the permissions it can exercise, and the actions it attempts. It gives customers a way to review an exact add-on version, stop a disallowed action at a supported enforcement point, and show what happened afterward. **Local laptop installations are in scope.** A repository can show the approved version of a skill while a developer runs an edited, downloaded, or independently installed copy. These are separate observations that Zasp needs to reconcile. [Current product scope](../../README.md) · [Claude Code skill locations](https://code.claude.com/docs/en/skills) · [Codex skill locations](https://developers.openai.com/codex/skills)

## Users and the pilot journey

| User | Job in the product |
| --- | --- |
| Developer or agent owner | See what's on their laptop or in their repository, check a new add-on privately, and understand a blocked action and their options. |
| Endpoint or platform administrator | Enroll a pilot group through device management, connect services and SDKs, verify health, and manage upgrades and removal. |
| AppSec or security engineer | Review an add-on version, investigate what an agent can reach, simulate a policy, and roll it out to selected agents. |
| SOC responder | Reconstruct one session, request containment at a supported surface, and verify the outcome and expiry. |
| Compliance reviewer or security lead | See the policy version, approvals, results, and known coverage gaps in an export they can share internally. |

1. A developer runs a local inventory preview. It finds a repository skill and a separate personal copy. The developer can see machine-local details. No upload occurs during the preview.
2. An administrator connects GitHub and enrolls a handful of managed laptops. A security engineer scans the repository bundle in CI and approves that exact version in the pilot Environment.
3. A laptop reports the repository version and a locally edited version as separate installations. Zasp shows where each copy exists, how it was identified, which one was observed in use if the harness reports it, and which copy needs review.
4. A security engineer simulates a rule, then enables it for a pilot group. A test agent can create a draft in a staging ticket system, while a send to a destination outside the approved group is blocked before the tool runs. The developer sees the rule and how to proceed. Sessions shows the decision and the available evidence of enforcement.
5. The responder isolates a test session where supported, verifies that subsequent governed calls are blocked, and sees when the control expires. Compliance can export the policy version, approval, test evidence, and coverage limits.

## V2-01 Connect inventory, permission, and action evidence

**User story.** As a security engineer, I want to start from an agent or finding and answer which identity it uses, which versions are present, what that identity can reach, which action occurred, and how confidently Zasp can tie those facts together.

**Requirements and UX.** Add the evidence to the existing Agent detail, Attack Paths, and Sessions views. On Agent detail, separate configured access, evaluated effective permission, and observed activity. Display source, last observed time, and freshness alongside each claim. Show permission as unknown where the provider cannot establish it. An Attack Path step labels whether its evidence represents possible reach or a resource actually touched. An action opens in the existing Session timeline with a detail view for the principal, tool, target, outcome, policy version, and linked add-on versions. Default to metadata. Expose only the evidence the caller is authorized to read.

Extend the existing correlation pipeline. A supported adapter should report a scoped action ID, its harness or provider session ID, agent binding, principal reference, tool and operation, resource or destination classification if available, time, and evidence source. Keep pre-action intent, policy decision, and observed result as separate records joined to the same action. Resolve identities from authenticated bindings and retain existing correlation confidence levels. A caller-provided ID, temporal proximity, or a device installation alone cannot establish exact attribution. Keep historical daily gateway rollups readable as rollups. Use existing trace identifiers and map OpenTelemetry GenAI spans where the adapter supports them. Give decision points a bounded policy snapshot and a small set of verified context inputs so inline evaluation can run without a graph traversal. [Agent access model](../../services/platform/apiserver/agent_access.go) · [Runtime event model](../../services/platform/runtimeevent/runtimeevent.go) · [OpenTelemetry GenAI example](https://opentelemetry.io/blog/2026/genai-observability/)

**Acceptance.** From one instrumented test action, an authorized analyst can follow `Agent → Identity → Tool → Target` and open the exact Session event with its policy and outcome. A matching installation with no load evidence displays “Installed” only. Two overlapping sessions, a caller claiming another agent, a stale graph, and duplicate or out-of-order observations never produce a false exact join. Graph availability does not change an inline decision.

## V2-02 Enforce before an action and verify containment

**User stories.** As an agent owner, I want to know why Zasp stopped an action and how to adjust it. As a platform engineer, I want the same policy for a local coding agent, a managed service, and my own application where they expose compatible enforcement points. As a responder, I want to restrict one session and verify what the restriction accomplished.

| Surface | Proposed behavior | User experience and limits |
| --- | --- | --- |
| Hosted MCP/model gateway and customer gateway | Preserve existing text inspection. Extend the routed action context where an authenticated binding supports it. | Guardrails shows whether control applies to the prompt, MCP call, or response. Traffic outside the routed path has its own coverage state. |
| Claude Code and Codex | Start with Claude Code managed `PreToolUse` for documented tool events. Add supported Codex surfaces after validating the deployed versions and managed configuration. | The developer sees a reason, action ID, and a next step in the harness. The coverage view shows which operations the hook can stop. A post-action hook records outcomes and cannot undo side effects. |
| Claude Enterprise and other SaaS | Integrate Claude Enterprise inference hooks as the first provider-side adapter. Verify signature, event identity, policy scope, and provider timeouts before supporting enforcement. Evaluate other providers by capability. | Integrations distinguishes `Audit only`, `Can block before action`, and `Can contain`. A supported enterprise account can be governed on an unmanaged device through its provider. |
| Homegrown agent | Ship a Python wrapper first with `before_tool` and `after_tool` around real execution. The wrapper carries an authenticated workload identity and shares the same action contract and correlation ID. | Developers can start in monitor mode from a quickstart, see decisions in Sessions, and enable blocking for selected tools. Calls outside the wrapper are reported as outside coverage when known. |
| Containment | Reuse the supervised isolation workflow where possible. Extend it to pause future supported calls for an exact session or agent. Add provider cancellation, identity revocation, or device process stop for individually verified adapters and explicitly authorized scopes. | Sessions → **Contain** previews the scope, affected surface, expiry, and required approval. The result lists what was requested and what each adapter verified. Show unknown or failed effects and restore status explicitly. |

Use the existing `allow`, `block`, and `redact` verdict concepts. Monitor is a policy mode that records what would have happened. An adapter declares which verdicts it supports. For a service that supports only allow/deny, the operator must choose a supported policy action before rollout. Keep response approvals distinct from any adapter that can pause a live tool call. On a block, show a permitted way to retry if one exists and tell the user which policy owner can review the restriction. A retry is a new action with a new policy check. [Existing decision API](../operations/guardrail-decision-api.md) · [Current response actions](security-agent-action-readiness.tsv) · [Claude Code hooks](https://code.claude.com/docs/en/hooks) · [Codex hooks](https://developers.openai.com/codex/hooks) · [Claude Enterprise inference hooks](https://support.claude.com/en/articles/16059458-inference-hooks-overview)

**Acceptance.** A permitted action completes. A configured denied action reaches neither the target nor the side-effect recorder. Retrying an identical decision request cannot issue conflicting receipts. A temporary isolation stops new calls for its exact scope and leaves another session operational. An already-running action, failed verification, unsupported cancellation, or failed expiry cleanup remains visible as such. Authorization, device or service authentication, and policy behavior are tested separately for each adapter.

## V2-03 Cover managed laptops and browsers

**User stories.** As an endpoint admin, I want to deploy Zasp to one managed group and know which devices have checked in, loaded the intended policy, and reported at least one signal. As a developer, I want to preview what Zasp sees on my machine and inspect my own protection status.

**Laptop path.** Pilot macOS with a signed, notarized package and managed harness configuration deployed through Jamf. Support a Windows package and Intune profile in the next rollout stage, or pilot Windows first when the participating fleet requires it. Enrollment uses organization-issued configuration to exchange for scoped per-device credentials. Package and profile management cover installation, upgrade or rollback, and removal. Track device heartbeat, package and harness versions, capability, loaded policy version, and last complete inventory separately. An MDM assignment can establish the expected cohort. A check-in and adapter acknowledgment establish actual coverage. Surface devices that are expected but have never checked in, stale, offline, unsupported, or unenrolled. Show a count of enrolled devices only if the expected fleet denominator is unavailable. [Jamf deployment](https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Package_Deployment) · [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) · [Microsoft Intune](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32)

**Browser path.** Use provider-side enforcement first for supported enterprise accounts. Add a managed Chrome extension and then Edge for selected AI origins and managed profiles. Begin with app and session metadata and a coverage report. Add inspection or blocking only on named flows the extension can reliably observe before dispatch. Collect content only under the Environment's approved collection mode. For integrations that can only see that an app was opened, label the signal as app usage and leave tool and action details unknown. Browser, provider, and device observations may overlap. Use verified evidence joins to deduplicate and show the contributing sources. [Chrome force-install policy](https://support.google.com/chrome/a/answer/6306504) · [Edge force-install policy](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/extensioninstallforcelist)

**UI and CLI.** In Sources → Sensors, add a Devices tab with an **Enroll pilot** flow. It lets the admin choose the Environment, OS, MDM or browser channel, pilot group, and collection mode, then download the package/profile instructions. Device detail shows supported harnesses, coverage, installations, and last reports. **Retire device** stops future ingest for its credential, with removal progress reported separately. An employee can use `zaspctl device status` and `zaspctl device doctor` to verify enrollment, adapters, and next steps without admin dashboards. The [CLI section](#cli-experience) defines the other commands.

**Acceptance.** Test signed install, first check-in, policy receipt, upgrade, rollback, and removal on a real test fleet for each supported rollout platform. Exercise managed Chrome and Edge against supported and unsupported origins before claiming coverage. A disconnected device shows stale coverage. Revoking enrollment prevents new submissions and respects retention of historical evidence. Cloning a package or guessing a device ID does not enroll a second device as the first.

## V2-04 Detect deviations and propose guardrails

**User stories.** As an agent owner, I want to declare the actions my agent is supposed to perform. As an AppSec engineer, I want Zasp to identify deviations and suggest a rule I can understand, simulate, edit, and roll back.

**Product behavior.** On Agent detail, let the owner describe allowed actions, resource classes, destinations, and approval requirements. Store a versioned structured specification alongside an optional description. Use contextual signals such as action risk, resource sensitivity, declared scope, sequence, novelty, and signal confidence. Start with policy and statistics built from observed facts. Add an optional classifier for ambiguous events, with bounded input and evidence references. Observed frequency can inform a suggestion. It cannot grant authority or override an explicit restriction. Generated text produces typed policy drafts. The existing policy approval and enforcement model owns what can be activated. [Existing detectors](../operations/guardrail-decision-api.md#what-it-does-and-does-not-do) · [Existing runtime and approval requirements](../internal/agent_security_platform_PRD_v1.5.md#10-runtime-protection)

**UX.** In Guardrails → **Suggestions**, show the proposed conditions and action, which purpose or behavior prompted the proposal, evidence and freshness, available enforcement surfaces, and what may be affected. The flow is **Review → Simulate → Monitor → Enforce**. Simulation shows the date range, data completeness, matched sessions, and estimated would-block rate by surface. Monitor mode records would-blocks with real execution continuing. Promotion is scoped to a selected cohort. Revert activates a prior policy as a new recorded revision and shows pending acknowledgments. An agent with too little telemetry shows “Insufficient activity” and can use the declared specification or remain in monitor mode. Models degrade to deterministic policy when unavailable.

**Acceptance.** A support agent that reads assigned cases and drafts responses is allowed. Its attempt to send a response outside the approved scope produces an explainable deviation. Repeated out-of-scope actions cannot make that pattern allowed. A generated rule remains inactive until reviewed and promoted by an authorized user. A model or graph outage leaves the active deterministic rules in place. The product reports coverage, false blocks measured in the pilot, policy rollout state, and decision latency per supported surface.

## V2-05 Vet local and repository add-ons throughout their lifecycle

**User stories.** As a developer, I want to check a downloaded or edited skill without publishing its source. As an AppSec engineer, I want to approve one exact version and see where it is installed, used, or out of date. As an admin, I want to revoke approval for a version and know where that revocation is enforced.

### Local installation discovery

1. Scan documented roots for supported harnesses and enabled profiles. For Claude Code start with managed, personal, and scoped project skill directories and enabled plugin bundles. Include a working tree's uncommitted files. For Codex add user, project and managed skill locations and plugin sources where supported. Configured extra project roots and synced skills are separate coverage rows. Inventory configured local and remote MCP declarations on supported harnesses without launching local servers. Report a SaaS-only or built-in skill as a provider observation when supported and report its local content as unavailable. Maintain a versioned support matrix by harness, OS, skill source, and signal. [Claude Code skills](https://code.claude.com/docs/en/skills) · [Codex skills](https://developers.openai.com/codex/skills)
2. Build a bounded manifest of the skill entry file, included scripts and resources, and available dependency declarations or lockfiles. Use consistent relative paths and byte digests to identify a complete bundle across GitHub, CI, and laptops. Record resolved dependency identity when available, separately from the bundle digest. A lockfile and a deployed dependency observation answer different questions. Keep publisher and source origin as independent approval inputs. Same-name copies stay distinct. A path or repository commit establishes provenance. Identical installed bytes require a matching, complete manifest. Missing or unreadable files, changes during enumeration, and external links outside approved roots produce partial or unknown results. Discovery reads only approved paths, excludes secrets and unrelated personal files, and executes no add-on code.
3. Record each installation independently with its device or repository, source, user or project scope where known, referenced version, and last observation. Put a reconciled device inventory into effect only after a complete scoped report; a partial report must not remove existing observations. Detect changes on a bounded cadence and on supported install, update, or file-change signals. When a later complete report no longer sees an installation, show it as removed. Local or provider runtime signals are required to claim it was loaded or invoked. A hook that cannot establish which bytes were loaded reports that limitation.
4. Evaluate the local version against Environment policy and version approval. New bytes enter review; an approval for a prior version never transfers automatically. Where a managed adapter can verify a version before loading, it may deny a revoked or unapproved version according to policy. Where an adapter can only inventory, show a finding and a verified removal or replacement path if available. An approval in the console does not assert that a copy was removed.

### Private scanning, approvals, and drift

Start with skills and MCP declarations. Extend the same records to plugins, sub-agents, commands, and hooks in stages. Combine static checks on skill instructions and bundled code with dependency version, provenance, and advisory checks. For MCP, track the declaration and available tool or permission changes. A remote server can expose its advertised tool schema without exposing its underlying server code. Track remote implementation identity as unknown unless independently attested. Evaluate existing scanners on a versioned fixture set before choosing an engine. Support scan modes and data flows explicitly. Local checks can submit only findings and digests. A private, centrally scanned bundle needs an authorized upload to a tenant-controlled location, bounded retention, and an approved scanner. A model-assisted scan that uses a remote service is a separate configured data flow. [Cisco Skill Scanner](https://github.com/cisco-ai-defense/skill-scanner) · [NVIDIA SkillSpector](https://github.com/NVIDIA/SkillSpector) · [AIR add-on lifecycle](https://aws.amazon.com/marketplace/pp/prodview-tdnubw7ntts6m)

Add optional behavioral inspection after static scanning and version governance work. Use isolated, authorized artifacts and synthetic resources, with bounded execution, no production credentials, and no access to a customer device. Compare observed activity with declared capabilities and record evidence. Keep this mode separate from normal discovery, uploads, and CI. AIR provides a benchmark for scan, approve, rescan, and revoke across multiple add-on types. Metano SkillTracer provides a benchmark for combining static and observed sandbox evidence. The Zasp workflow keeps employee and company submissions private. [AIR supply-chain framework](https://www.air.security/blog-posts/agent-supply-chain-framework) · [SkillTracer analysis and submission policy](https://labs.metano.ai/scanner/faq)

**UX.** Add an **Add-ons** tab under Tools & MCP with filters for type, harness, location, owner, review state, and observed use. Detail has **Versions**, **Installations**, **Scans**, and **Usage**. Show two separate risk dimensions, what the add-on could reach and what the scan found, alongside review state. A clean scan result means no finding from that scan. Approving a version shows the exact digest, provenance constraints, scope, installations, and any expiry. Updating or revoking a decision shows which adapters can apply it and their acknowledgments. Findings and device views link directly to drift rows. A developer can use `zaspctl addons inventory --local`, `zaspctl addons scan <path> --local`, or an explicitly authorized CI submission.

**Acceptance.** The registry recognizes matching repository and laptop bytes while retaining the two observations. A same-name personal copy changed on disk produces a new, unapproved version. A dependency or remote tool schema change triggers reevaluation under its own observed provenance. On a supported policy point, a verified revoked version is denied. For an inventory-only device, the UI reports that the installation is present and unprotected by a prevention policy. An incomplete scan, unreadable root, or unknown usage appears as unknown or partial. Local-only scans work without a Zasp account, upload, or execution of the add-on.

## V2-06 Verify the side effect and run regressions

**User story.** As an AppSec engineer, I want to verify a proposed policy in staging and show that it prevented a protected side effect while allowing legitimate work. When an artifact, tool schema, or active rule changes, I want to rerun the checks that apply to it.

Extend Red Team with **Policy verification** from an agent, finding, or draft policy. Run bounded scenarios against authorized development or staging targets using synthetic records and a test-only destination. A scenario defines the expected decision and the side effect it should permit or prevent. Include a positive control proving that an allowed action can reach the recorder. Join the target receipt to the policy decision and record four separate outcomes, `passed`, `unexpected effect`, `inconclusive`, and `unsupported`. An absent receipt counts as evidence only if the positive control and recorder health establish that the observation could have been captured. Preserve the product's existing non-production and credential restrictions. Reuse scheduled and change-triggered runs for selected scenarios. Extend the triggers to relevant artifact, tool schema, and policy changes, with deduplication and rate limits. Keep Attack Lab verification separate and expose it only for validated environments. [Current Red Team workflow](../getting-started/user.md#6-red-team-tests) · [Current verdict implementation](../../services/platform/redteam/probes/catalog.go)

**UX and acceptance.** The run detail shows expected versus observed behavior, policy and artifact versions, scope, and links to the session and receipt. A blocked staged send has a decision receipt and no corresponding target write, while the permitted staged send produces both. A disconnected recorder is inconclusive. Updating the approved skill triggers the mapped regression once. Reports distinguish response-marker checks from tests that verified a side effect.

## V2-07 Make setup, evaluation, and customer proof repeatable

**User stories.** As an evaluator, I want to find a meaningful local or cloud issue without configuring the whole product. As an enterprise admin, I want to know which integrations were verified, what data leaves my Environment, and whether setup or revocation finished. As a security lead, I want a report that can support a rollout decision.

Offer two starting paths. **Scan this device** runs a local inventory and optionally scans one identified bundle before sign-in. It shows supported and skipped locations and can produce a local report. **Connect a source** takes an authorized user through read-only GitHub or a supported cloud source, first sync, and a first finding with source freshness and a next action. An evaluator chooses whether to share metadata with a pilot Environment. A pilot report gathers coverage, observed findings, approved versions, and tested outcomes under the current user's permissions. Mark sample data as such. Provide an export that works without screenshots and distinguishes missing, omitted, and verified evidence. [Current onboarding and demo data](../getting-started/user.md#2-connect-your-first-source) · [Metano's evaluation flow](https://metano.ai/eval)

Before presenting a surface as verified, run it end to end in the deployed product with a real test account, provider, or managed fleet. Start with GitHub, one real AWS discovery and approved remediation path, and the first governed harness. Verify the hosted gateway with an actual supported provider or MCP server. Prioritize the existing IdP, Kubernetes, and SaaS connectors by pilot need. Track a verification date, version, verified capabilities, and known gaps per surface. Exercise real admin and member sign-in, authorized onboarding and deprovisioning, approvals and notifications, policy rollback, upgrades, revocation, cleanup, exports, and recovery in the release profile. Reuse the V1 release gates and Security Agent approval model. Provide a trust and data-flow summary covering access, retention, deletion, subprocessors, and deployment boundaries. Framework mappings, attested controls, and actual certification status appear as separate claims. [V1 enterprise release gates](../internal/agent_security_platform_PRD_v1.5.md#21-mvp-release-gates) · [Current launch verification](../internal/mvp-launch-plan-2026-11-12.md#state-on-2026-11-14)

**Acceptance.** A pilot participant who did not deploy Zasp can generate a local report, then join a pilot and complete a real source connection. An authorized reviewer can export the evidence of a verified controlled action, list the surfaces and policy versions tested, and explain any gaps. A failed or stale connection displays a recovery action. A customer cannot infer production support from a fixture result or an installation count.

## CLI experience

`zaspctl` is the proposed user CLI name. The repo's `./zasp` remains the operator entry point for deploying and operating Zasp. The implementation plan should treat these as distinct credential and command contexts. [Current operator CLI](../../zasp)

| Command shape | Who uses it and what they see |
| --- | --- |
| `zaspctl addons inventory --local [--project <path>]` | Developer. Show selected roots, add-on type, harness, location scope, version if complete, and skipped roots. Runs before sign-in. |
| `zaspctl addons scan <path> --local [--json]` | Developer or CI. Show version and scan findings, reasons and completeness. Local mode works without network access. |
| `zaspctl auth login` | Authorized user. Use the existing identity provider in the browser, select an Environment, then return a limited CLI session to the initiating client. Dedicated CI credentials use separate, narrow permissions. |
| `zaspctl addons submit <report> --mode findings-only --environment <id>` | CI or authorized developer. Submit digest, coverage and findings, then print the review link. A separate, explicitly configured private upload mode may submit eligible source. |
| `zaspctl device status` / `zaspctl device doctor` | Developer or endpoint admin. See enrollment, loaded policy, supported adapters, stale components and a next step. The admin distributes the enrollment profile through MDM. |
| `zaspctl guardrails simulate <revision> --agent <id> --since <time>` | Security engineer. Start a scoped replay or retrieve its receipt. Results link to coverage and representative matches. |
| `zaspctl sessions show <id>` / `zaspctl evidence export --session <id>` | Responder or auditor. Read the same scoped decision and outcome evidence as in the UI. Export hands off to the browser for fresh authentication and the authorized report and download flow. |

Local commands display full or relative file paths on request. Reports prepared for sync redact sensitive paths by default. An authenticated mutation prints its scope and returned receipt. Machine output uses a stable JSON envelope with `schema_version`, `status`, `coverage`, `items` or `result`, and actionable reasons for skipped work. Human diagnostics go to stderr in JSON mode. Use `0` for a completed command, `2` for input or authorization errors, `3` for incomplete or unavailable evaluation, and `10` for a complete scan that violates an explicitly selected CI policy. Findings in an interactive scan are results. Credentials belong in managed configuration, local secure storage, or the CI secret channel and stay out of output and command history.

This local output shows a developer's edited copy of a skill alongside the project copy.

```text
$ zaspctl addons inventory --local --project .
Claude Code    Project   ticket-helper   sha256:ab12…   Installed
Claude Code    Personal  ticket-helper   sha256:19d4…   Installed
2 installations, 2 versions. Usage evidence unavailable on this device.
Local preview complete. No data uploaded.
```

## UI conventions

- **Inventory state and approval state stay separate.** A version can be installed, unobserved in use, approved in a different scope, and unsupported for blocking. Show the relevant states together without collapsing them into a single badge.
- **Enforcement is a capability and a current state.** Show both `Can block before action` and `Monitor` when the adapter supports blocking and is currently observing. Distinguish an acknowledged version, a pending rollout, stale coverage, and a route outside coverage. Disabled controls identify the missing capability or permission when the viewer is allowed to see it.
- **Evidence is navigable.** Link an add-on version, installation, finding, policy revision, session event, and response approval through scoped IDs. Default to the current Environment and preserve filters across related views. Label fixture data and omitted or unavailable evidence in the detail view and exports.
- **Privacy controls are visible at the point of use.** Before upload or enrollment, show which data categories will be sent and who can read them. In a block response, show what action was stopped, the policy reason, and the permitted next step. Avoid including prompt, secret, or raw file content in these messages.

### Shared records and semantics

| Record | Required meaning |
| --- | --- |
| **Enforcement point** | An authenticated device adapter, provider hook, gateway, or SDK binding. Reports supported action kinds, modes, last heartbeat, current applied policy revision, and failure behavior. |
| **Action attempt** | Stable ID in the adapter's scope, time, operation and resource classification, available session and tool or trace IDs, and evidence for actor, workload, and version references. Distinguish missing references from verified ones. |
| **Decision and outcome** | Decision ID, action ID, policy revision, reason, mode, verdict, time and evidence source. The outcome independently records whether enforcement was applied or whether the action completed, with the exact supported receipt. |
| **Add-on version** | Immutable version identifier or an explicit partial observation. Store manifest digest, digest method version, origin/commit references, dependency resolution coverage, and bounded scan metadata. Every scan also identifies the scanner and rule-set version. |
| **Installation observation** | A version or unknown version observed at a specific source, device and user/project scope when available. Keep first/last seen and observation state. An installation and a runtime usage observation have different meanings. |
| **Review decision** | Actor, exact add-on version, allowed origins, scope, state, reason, timestamp, and expiry or superseding decision. Installed content and review state form separate histories. |

An illustrative action check returns a receipt before the action runs. The adapter identity and its authorized scope come from verified authentication. Client labels are treated as evidence and checked against that scope.

```json
{
  "decision_id": "example-decision-42",
  "action_id": "example-action-42",
  "mode": "enforce",
  "verdict": "block",
  "reason_code": "destination_outside_scope",
  "policy_revision_id": "example-policy-revision-7",
  "coverage": "pre_action_supported"
}
```

The check's minimum request carries an action ID, adapter session reference if available, action kind, operation and bounded target descriptors. Version and identity observations can be supplied only by capable adapters. The outcome report references the decision and supplies the observed effect or a specific reason the result is unknown. Hook deadlines and hosted API failures must be distinguishable from a policy verdict. A locally cached policy records its own revision and decision for later delivery. Provider callbacks retain their own transport and response encoding.

### Authorization, reliability, and data

- Use the current Organization, Workspace, and Environment authorization model. Scope device, workload, provider and CI credentials to the operations each needs. Separate ingest, read, review and activation permissions. Derive actor and scope from authenticated bindings. A device's credentials cannot read other devices or approve its own artifact. Review, containment, and export operations follow the existing authorization and freshness rules.
- Bind decisions to the scoped action ID. Retries with the same input return the same receipt. Reuse with conflicting input returns a conflict and does not apply a different action. Review transitions and rollout changes carry an expected version. Preserve audit history and handle late or duplicate outcome reports without changing a prior verdict.
- Reuse existing API pagination, mutation idempotency, error shapes, and scoped data access. Expose `pending`, `partial`, `stale`, `unsupported`, and failure reasons explicitly. Keep policy modes, installation state, and scan verdict independent. Batch and bound device submissions. Mark a snapshot incomplete if its expected data was truncated.
- Use signed, cached policies where the adapter supports them. Configure, display, and verify per-surface timeout and stale-policy behavior. Treat an unsupported failure mode as lack of enforcement coverage for a policy that requires it. A supported local policy path should continue using a valid snapshot when the graph, model service, or control plane is briefly unavailable. Asynchronous analysis can enrich the next decision or a later investigation.
- Default to metadata-first collection. Raw prompts, tool arguments, skill bundles, local absolute paths, and credentials have different collection policies. A local artifact preview executes none of the files and sends nothing. Any configured private artifact upload or content retention must be visible in External Data Flows and Data & Retention, with scoped access and deletion. Never put content or secrets into diagnostics, analytics, or general audit fields. Reuse encrypted evidence storage and expiring download grants for retained exports.
